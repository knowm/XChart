- [x] #906 — Stacked Bar With Secondary Line — *2026-07-06* — **Draft PR #994** (branch `issue-906-stacked-secondary-axis-line` → develop). - [x] #465 — Stacked Area charts — *2026-07-02* — **Implemented** (PR #986, branch `issue-465-stacked-area`). Stacking machinery was bar/stick-only; `setStacked(true)` + `Area` render style silently produced overlapping, clipped areas. Root causes: (1) `AxisPair` recomputed the stacked Y-axis min/max only for bar/stick styles → axis clipped at raw max instead of stack sum; (2) `PlotContent_Category` advanced the stack accumulator by `(yTop - yBottom)`, which is 0 for area/line (bars only worked because they set `yBottom=0`); (3) area always filled from the plot baseline so translucent layers overlapped. Regression test `issue465StackedAreaScalesToStackSum` + side-by-side demo `TestForIssue465.java`. **Scope:** CategoryChart (categorical X) only; true continuous XYChart stacking is a separate larger follow-up (needs `isStacked` on `XYStyler` + accumulator/band-fill in `PlotContent_XY` + X-alignment for sparse X). 102 xchart tests pass, `fmt:check` clean.

- [x] #554 — CPU usage with real time xy chart and lots of points — *2026-07-03* — **Closed** (maintainer). Posted analysis + guidance. - [x] #634 — Negative Y-axis label with all-positive data — *2026-07-07* — **PR #996** (branch `issue-634-negative-axis-labels` → develop). All-positive data (60M..23B) rendered a `-2,000,000,000` label in the bottom plot margin. Root cause: `AxisTickCalculator_.calculate()` deliberately overshoots the tick range — `getFirstPosition()` returns `minValue - (minValue % gridStep) - gridStep` (one step below min) and the loop runs to `maxValue + 2*gridStep`. When `minValue < gridStep`, `minValue % gridStep == minValue` so firstPosition = `-gridStep` (negative). Gridlines/tick-marks already clip to plot bounds (`PlotSurface_AxesChart`), but the label renderer (`AxisTickLabels`) clips to the taller axis-*column* bounds, so overshoot labels leak into the margin. Fix: after the do-while settles, prune ticks whose pixel is outside `[margin, margin+tickSpace]` (⟺ value outside `[min,max]`); done post-loop so uniqueness/fit termination is untouched, and skipped if it would empty the axis. Applies to all numeric X/Y axes (also removes phantom above-max ticks like the `24B` here). Note: the formatting function is still *called* during generation on the pruned values (side-effect only; label discarded) — acceptable, formatters should be pure. Verified via before/after PNG (NEG label gone; axis shows 2B..22B). `RegressionIssue634Test` + demo `TestForIssue634`; full xchart suite 130 pass, fmt clean. Demo initially copied the reporter's `setYAxisMin(dataMin=60M)`, which (correctly, post-fix) pushed the `0` tick out of range → follow-up commit dropped it so the `0` baseline tick stays (bug still repros at default min=0 since firstPosition = `-gridStep`). Pre-existing quirk surfaced: `CategoryChart` anchors bars at 0 regardless of `setYAxisMin` — out of scope. **Filed follow-up #997** for the structurally cleaner fix (make `AxisTickLabels` clip to the plot band like gridlines/marks, or generate in-range from the start + stop calling the formatter on out-of-range values) — deferred from #996 to avoid changing grid-step selection with no pixel-baseline tests.
